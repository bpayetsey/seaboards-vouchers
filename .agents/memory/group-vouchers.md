# Group Vouchers (Seaboards Golden Jubilee)

Resort group-voucher offer for Seychelles, currency SCR. Lives in `artifacts/group-vouchers` (web, root path) + `artifacts/api-server` (Express) + `lib/db` schema (`groupOrders`, `voucherLines`).

## Order modes
- **independent** — each payer buys their own voucher; each paid line gets its own `voucherCode`. Order becomes `complete` when all lines paid.
- **split** — all-or-nothing shared voucher. Shares are equal-split (remainder on first line) OR explicit `share_minor` that must each be positive and sum to room total. Order `complete` (with a single `splitVoucherCode`) only when every line is paid.
- **flat** — simple per-person links: one `per_person_minor` applied to every line, no apartment/nights. Behaves exactly like independent for payment/voucher/completion/sweep (the server branches on `mode === "split"`, so flat falls into the independent path). Created from the inline storefront "Buying for a group?" section.
- **Names are optional:** `organiser_name`/`payer_name` are nullable in the API; server falls back to the email (`organiser_name || organiser_email`, `l.payer_name || l.payer_email`). The flat storefront form only collects emails + amount.

## Pricing
Default rates major units: `one_bedroom=2300`, `two_bedroom=3750` per night. `MINOR_PER_MAJOR=100`. Amount stored in minor units. `amount = rate * nights * 100`.
- **Editable prices are admin-overridable** via `store_catalog_price` (itemId PK, rate, was). `getEffectiveCatalog()` in `storeCatalog.ts` merges overrides onto the static `CATALOG` defaults (falls back to defaults on DB error). Only the two apartment packages are editable (rate + strikethrough `was`); gift-voucher amounts are buyer-chosen.
- **Single source of truth, no drift:** the effective catalog must feed *every* pricing path. Storefront config + order validation (`priceFor`, async) AND group split pricing (`getRates`/`getRateTable`, async, mapped via `CATALOG_ID_TO_APARTMENT_TYPE`) all derive from it. Never read the static `CATALOG`/`RATES` constants directly in a new pricing flow — add to `getEffectiveCatalog` instead. **Why:** storefront and group order used to duplicate the same hardcoded numbers; an override that only updated one would silently mis-price the other.
- Admin endpoints `GET /admin/catalog-prices` + `PUT /admin/catalog-prices/{itemId}` (staff-gated). Server rejects non-integer/non-positive prices (does NOT round) so behavior matches the "whole positive amounts" error text.
- **Day Passes** are fixed-price storefront vouchers (`DAY_PASSES` in `storeCatalog.ts`; `type:"day_pass"` flows through the normal store_order→Stripe→voucher pipeline, no DB migration since `store_order.type` is free text). Pricing is **adults + children** (not a single guest count): `priceFor`/`nameFor` take `adults`+`children`+`extension`. Flat passes (`pricing:"flat"`, e.g. the room) charge `rate` covering `includedAdults` and IGNORE client `adults`; per_person passes charge `rate×adults` (adults≥1). Children (ages `childAges`, e.g. 2–10) always add `childRate` each. Server bounds: `children ≤ maxChildren`, `adults+children ≤ maxGuests`. Kids 11+ are booked as adults. Prices are hardcoded server-authoritative (no `store_catalog_price` override wired — future work).
- **Group split `amount_minor` is ONLY safe for open-value gift vouchers** (buyer chooses the value — nothing to tamper). Fixed-price items must NOT use the `amount_minor` split path: it trusts the client total (groupVouchers.ts only checks `>0`). Apartments split via `apartment_type+nights` (server-priced); day passes are **excluded from group split entirely** (UI shows a notice, only pay-in-full / pay-in-3). **Why:** routing a server-fixed price through `amount_minor` lets a buyer underpay.

## Stripe
- **Dynamic server-side `price_data` is intentional and correct here** — do NOT use a product catalog, despite the generic Stripe skill saying "never price_data".
- Connector id: `connector:ccfg_stripe_01K611P4YQR0SZM11XFRQJC44Y`. Packages: `stripe` + `stripe-replit-sync`.
- Server startup is **resilient**: if Stripe isn't connected, it warns and keeps serving (don't make it throw).
- Webhook registered with `express.raw` BEFORE `express.json`; verified via `stripe.webhooks.constructEvent` with the integration's webhookSecret. Managed webhook auto-registered on boot via `getStripeSync().findOrCreateManagedWebhook(...)`.

## Invariants (enforced after code review)
- Webhook `handleSessionCompleted` only transitions a line when `line.status === "pending"` AND `order.status === "open"` — never resurrect an expired/swept line.
- `startCheckout` reuses an existing open Checkout session for a line before creating a new one (avoids duplicate charges).
- `/api/group-orders/admin/sweep` is protected: requires `Authorization: Bearer <SESSION_SECRET>` (constant-time compare). Never world-callable.

## Server links
API returns RELATIVE links (`/pay/{token}`, `/group/{token}`); Stripe success/cancel URLs are absolute from request origin; frontend prepends `window.location.origin` for copyable links.

## Storefront + Pay-in-3 (direct-to-buyer)
- Separate from group-ordering. Home `/` = storefront (`pages/home.tsx`, currency **eur** — SCR usually unsupported by Stripe); the old group form moved to `/group-order` (`pages/group-order.tsx`, still SCR). Tables: `store_order`/`store_installment`/`store_voucher` in `lib/db/src/schema/storefront.ts`.
- Catalog/pricing live **server-side** in `storeCatalog.ts` — price is never trusted from the client (`priceFor` recomputes from catalog/gift).
- Instalment engine: charge instalment 1 today with `setup_future_usage: "off_session"` to save the card; daily cron `POST /api/storefront/jobs/charge-instalments` (Bearer SESSION_SECRET) charges the rest off-session. Finalisation is via the `payment_intent.succeeded` webhook OR the confirm endpoint retrieving the PI — `processPaidIntent` is the single idempotent sink keyed on `pi.metadata.orderId/instalmentNo`.
- **Cron duplicate-charge guard (enforced after review):** before creating each off-session PI, atomically claim the row with a conditional `UPDATE … SET status='charging' WHERE id=? AND status IN ('scheduled','failed')` and skip if 0 rows returned. Without this, a delayed/failed webhook leaves the row `scheduled` and the next cron run re-charges (Stripe idempotency keys only retain ~24h). Store `paymentIntentId` on the instalment after create.
- Graceful degrade: `getStorefrontConfig` returns `publishable_key:""` + `payments_enabled:false` when Stripe isn't connected; frontend shows "Preview mode" banner and disables checkout. Stripe pkgs `@stripe/stripe-js` + `@stripe/react-stripe-js`; Payment Element uses `confirmPayment({ redirect: "if_required" })` then calls the confirm hook.

## Client Account Dashboard (Clerk)
- Auth is **Replit-managed Clerk**, web side is **cookie-based** — do NOT add `getToken`/Bearer/`setAuthTokenGetter` on the web client. Server uses `@clerk/express` `clerkMiddleware`; the Clerk proxy middleware must run BEFORE body parsers (alongside the Stripe webhook raw route).
- `requireAuth` resolves the user's **verified primary email** (`clerkClient.users.getUser`) and exposes it lowercased; routes 401 unauth / 403 if no verified email. Protected routes: `GET /api/dashboard` and `POST /api/dashboard/group-orders/:orderId/lines/:lineId/resend` (owner-scoped reminder — order matched by id AND lowercased organiser_email, so an organiser can only re-surface links for orders they own; distinct from the public token-based `/api/group-orders/:statusToken/.../resend`).
- **Scoping rule:** every dashboard record is matched strictly to that verified email, case-insensitively via `eq(sql\`lower(col)\`, normalized)`. Aggregates across both flows — storefront (`buyer_email`) and group (`payer_email` for paid lines + `organiser_email`). Organiser-owned group orders are surfaced in full as `organised_orders` (any status, incl. zero payments) with per-line status/amount/pay_link and master voucher once `complete`.
- **Reminders send no email** — `resendLine`/`resendLineForOrganiser` just return the pay link; the "Reminder sent" toast is cosmetic.
- [Voucher email delivery](voucher-email-delivery.md) — issued vouchers are emailed via SendGrid; email-once + eventual-delivery design (state-based eligibility, webhook is the durable retrier). Other store emails are still stubs.
- Receipt URLs captured at webhook time (`receiptUrl` on voucher_line/store_installment, `firstReceiptUrl` on store_order); dashboard does a best-effort on-demand Stripe backfill when a paid record is missing one (never throws into the request path).
- Home `/` stays **public** (it's the storefront) — intentionally diverges from the clerk-auth skill's auth-redirect-home pattern. Existing token-based pay/group pages are untouched by auth.

## Staff Admin Dashboard
- Admin area (`/admin`, `/admin/orders`, `/admin/vouchers`) is gated **solely by Clerk identity + a `STAFF_EMAILS` allow-list** — the browser never holds the scheduler's `SESSION_SECRET`. `requireStaff` (Clerk verified primary email must be in `STAFF_EMAILS`) backs every `/api/admin/*` route; the daily charge job stays on its own `SESSION_SECRET` Bearer auth (unchanged).
- **`STAFF_EMAILS` must be set** (comma/space separated) or *all* admin endpoints return 403 by design (secure default). Without it the admin UI is unreachable even for signed-in users.
- Frontend guard: routes wrap in signed-in `Show` then `AdminShell` calls `GET /admin/me`; non-staff (403) redirect to `/`. Web stays cookie-based (no Bearer), same as the dashboard.
- Manual voucher issuance required making `store_voucher.order_id` **nullable** (standalone vouchers have no order).
- `retryInstalment` no-double-charge rule (enforced after review): idempotency key is `...-retry{attempts}`, but **`attempts` (and thus the key) may only advance when Stripe proves no money moved** — i.e. a *definitive* failure (`StripeCardError`/`StripeInvalidRequestError`/`authentication_required`). On an **indeterminate** failure (timeout, `StripeConnectionError`, generic API error) leave `attempts` unchanged so the next retry replays the SAME key and Stripe returns the original PaymentIntent instead of charging twice. Also retrieve any stored `paymentIntentId` before charging and short-circuit if it is already succeeded/processing. The `payment_intent.succeeded` webhook is the backstop. **Why:** advancing the key on every failure (the original bug) let a retry after a timed-out-but-successful charge create a second charge.
- Cancel = flip order to `cancelled` + set remaining `scheduled/failed/needs_action/charging` instalments to `cancelled`; the charge job only selects `['scheduled','failed']`, so cancelled rows are never re-charged. **No refunds** anywhere in admin.
- Redeem is atomic: `UPDATE … SET status='redeemed' WHERE code=? AND status='active' RETURNING` (then a post-check reverts if the matched row was expired) — two concurrent redeems can't both win.

## api-server dev has no watch (build-once)
The api-server dev script is `build && start` (esbuild bundle, then `node`), with **no file watcher**. Editing server/route code does nothing until you `restart_workflow "artifacts/api-server: API Server"` to force a rebuild. Only the web artifact (Vite) hot-reloads. **Why:** a route added to the running server returned 404 until the workflow was restarted — easy to misread as a routing bug.

## Binary (PDF) endpoints live outside Orval
Voucher PDF download endpoints stream `application/pdf` and are intentionally NOT in the OpenAPI spec / Orval JSON hooks. The web client hits them directly via `fetch(url, {credentials:"include"})` → blob → anchor download (see `artifacts/group-vouchers/src/lib/voucherPdf.ts`). Public confirmation variant `/api/vouchers/:code/pdf` treats the code as a capability token (knowing the code already grants redemption); dashboard variant `/api/dashboard/vouchers/:code/pdf` is `requireAuth` + owner-scoped (404 if the verified email isn't in the voucher's authorized emails). Shared voucher copy (terms, resort constants) lives in `lib/voucher-content`.

## "Pay in N" instalments are NOT a Stripe subscription
First payment saves the card to a Stripe Customer (`setup_future_usage: off_session`) and charges 1/N. Instalments 2..N live in the app DB (`storeInstallments`, due dates `INTERVAL_DAYS` apart), NOT in Stripe — there is no Stripe Subscription/Schedule object. Each future instalment becomes its own off-session PaymentIntent when charged.
**Critical:** the charge job (`chargeDueInstalments`) has NO built-in scheduler. It only runs when something POSTs to `/api/storefront/jobs/charge-instalments` (Bearer = `SESSION_SECRET`). Without an external daily trigger, instalments 2..N are NEVER collected.
**Trigger:** a Replit Scheduled Deployment runs `pnpm --filter @workspace/scripts run charge-instalments` (script `scripts/src/charge-instalments.ts`), which POSTs to that endpoint using `STORE_BASE_URL` (prod URL, shared env) + `SESSION_SECRET`. Job is idempotent (atomic row claim + Stripe idempotency), so daily retries are safe.

## Transactional voucher emails (SendGrid) are milestone-idempotent
Real emails go out via Replit-managed SendGrid (REST v3 over fetch; creds from connectors proxy like stripeClient). `sendEmail`/`sendVoucherEmail` are best-effort: they return a boolean and NEVER throw (so payment/webhook/charge-job paths can't break on email failure).
**Issuance rule in `processPaidIntent`:** a voucher must exist+be `active` whenever `fullyPaid` (regardless of `SETTINGS.issueOn`); deposit policy additionally issues a `pending` voucher on instalment 1. The fully-paid transition ALWAYS triggers the active voucher+PDF email — do not gate it behind `issueOn === "paid"`.
**Idempotency (critical):** `processPaidIntent` runs from BOTH the Stripe webhook and order-confirm paths, possibly concurrently. Each milestone email is claimed atomically via conditional UPDATE (`SET <milestone>_emailed_at=now() WHERE id=? AND <col> IS NULL RETURNING`) BEFORE sending; only the row-winner sends. If delivery returns false, the claim is rolled back (set col back to NULL) so a later run can retry. **Why:** plain read-check-then-send let webhook+confirm both send the same email; stamping unconditionally would also permanently suppress retries after a failed send. Columns: `store_voucher.pending_emailed_at` / `active_emailed_at`.

## Advance instalment payments + order numbers
- **Human-readable order numbers** (`SB-XXXX-XXXX`, Crockford base32) live on `store_order.order_number` and `group_order.order_number` (nullable + unique). Generator `newOrderNumber()` is in `lib/db` (shared by api-server and the backfill script — leaf packages can't import each other, so order-number identity is a DB-level concept). Shown on storefront thank-you, group pay-done, and dashboard order cards.
- **Advance "Pay in 3" payments must be COUNT-based, not slot-based.** `processPaidIntent` derives `paidInstalments = 1 + count(paid rows)` and `fullyPaid = paidCount >= installments`. **Why:** a buyer can pay instalment 3 before instalment 2; activating the voucher off "is the last slot paid?" would prematurely issue it. Count-based finalisation is order-independent.
- **One charge path, shared no-double-charge guard.** Both the daily cron and the dashboard advance-pay route (`payInstalmentsForOrder`) call the same `chargeInstalmentRow(order, inst, {finalize})`, which uses the same atomic claim (`UPDATE … SET status='charging' WHERE id=? AND status IN ('scheduled','failed')`) and the same Stripe idempotency key `store-order-${id}-i${n}`. Never add a second code path that charges an instalment — extend `chargeInstalmentRow`.
- Advance-pay route is email-scoped via `requireAuth`/`AuthedRequest.userEmail`; it re-reads the dashboard order after charging so the client re-renders the schedule.
- **Per-instalment receipt email** is sent from `processPaidIntent` (the shared idempotent sink) for any paid instalment row where `instalmentNo >= 2 && !fullyPaid` — i.e. intermediate instalments only. First payment already has the deposit "plan started" notice; the final/fully-paid payment delivers the voucher PDF, so those are NOT double-emailed. Must be placed BEFORE the `shouldExist` early-return (it fires regardless of voucher issue policy). Idempotency claim is `store_installment.receipt_emailed_at` (conditional UPDATE … WHERE IS NULL, release to NULL on delivery failure) — same milestone-claim pattern as `pending/voucher_emailed_at`. **Why:** both the daily cron (webhook→processPaidIntent) and dashboard advance-pay (chargeInstalmentRow finalize:true→processPaidIntent) finalise instalments through this one sink, so claiming there guarantees exactly one receipt across both paths.

## WhatsApp marketing broadcasts (admin)
- Staff tool under `/admin/whatsapp/audiences` (import CSV contacts, opt-outs, audiences) + `/admin/whatsapp/campaigns` (template composer, send/schedule, per-recipient delivery report). Tables in `lib/db/src/schema/whatsapp.ts`. Server libs: `whatsappClient.ts` (Meta Graph **v21.0** Cloud API), `phone.ts` (E.164 via libphonenumber-js), `whatsappCampaigns.ts` (business logic + sender engine + webhook processing). Routes in `routes/whatsapp.ts`, staff-gated like other admin routes.
- **Only Meta-approved templates can be sent** — the composer's template list comes from `GET /admin/whatsapp/config` which calls Meta's message_templates API; freeform body text is never sent. `config.configured=false` ⇒ frontend preview mode (drafts allowed, send/schedule disabled), same graceful-degrade pattern as Stripe/storefront.
- **Webhook is public + raw-signed**, registered in `app.ts` BEFORE `express.json` (like the Stripe webhook): GET verify (hub.challenge vs `WHATSAPP_WEBHOOK_VERIFY_TOKEN`) + POST with `X-Hub-Signature-256` HMAC verified against `WHATSAPP_APP_SECRET`. Processes delivery-status updates (sent/delivered/read/failed) onto `whatsapp_message` rows and STOP/opt-out keywords → flips `whatsapp_contact.opted_out`.
- **Eligibility rule:** a contact is reachable only when `consent === 'opted_in' && !opted_out`. Sender engine skips ineligible contacts.
- **No duplicate sends (enforced after review):** dispatch is concurrency-safe via two defenses — (1) a UNIQUE constraint on `whatsapp_message(campaign_id, contact_id)` + `onConflictDoNothing` at enqueue (hard dedupe of rows), and (2) an atomic per-message claim `UPDATE … SET status='sending' WHERE id=? AND status='queued' RETURNING` BEFORE the Meta call — a dispatcher that gets 0 rows skips it. Campaign is marked `completed` only when no row is still `queued`/`sending`. **Why:** the original read-then-send let two concurrent dispatchers (e.g. a 'now' send racing the backstop, or duplicate scheduler ticks) blast the same recipient twice. Same atomic-claim pattern as `chargeInstalmentRow`. `contact_id` is nullable (NULLs distinct) so deleted-contact orphans don't violate the constraint.
- Dispatch job (`dispatchDueCampaigns`) is Bearer `SESSION_SECRET` at `/whatsapp/jobs/dispatch` — same external-trigger pattern as the instalment cron (no built-in scheduler; needs a Scheduled Deployment to fire scheduled campaigns). Optional `WHATSAPP_SEND_DELAY_MS` (default 250) throttles per-recipient sends.
- **Daily-batch cap (`whatsapp_campaign.daily_limit`, nullable, UI default 2000):** dispatch counts successful sends in the trailing rolling-24h (`sentAt >= now-24h`), sends only up to `max(0, limit - sentInWindow)`, increments the run counter ONLY on `result.ok` (matches Meta: failures don't count), and leaves the rest `queued` so the campaign stays `sending` and the next scheduled dispatch resumes it. NULL = send whole audience at once. Repeated runs are idempotent (cap recomputed each run).
- **Cap enforcement needs a per-campaign lock (enforced after review):** `dispatchCampaign` wraps the run in a Postgres session advisory lock `pg_try_advisory_lock(hashtext('whatsapp_dispatch'), hashtext(campaignId))` held on a dedicated `pool.connect()` client for the whole send loop; if not acquired it skips. **Why:** the atomic per-row claim prevents *duplicate* sends but NOT cap *overshoot* — two overlapping dispatchers (manual "send now" racing the daily scheduler) would each read the same headroom and together exceed the limit. The lock serializes headroom reads. `runDispatch` is the inner (unlocked) worker; never call it directly.
- **Template header media (image/video/document):** `whatsapp_campaign.header_media_id`/`header_media_type` reference a pre-uploaded Meta media id, NOT a link — `sendTemplateMessage` emits the `header` component BEFORE `body`. **Why:** link-based headers hit Meta error 131053 ("media upload error") when Meta can't fetch the URL; a reusable media id (~30d) avoids it. `header_media_type` is enum-validated server-side (image|video|document). `WhatsappTemplate.headerFormat` (NONE|TEXT|IMAGE|VIDEO|DOCUMENT) drives whether the composer shows the upload field.
- **Media upload route `POST /admin/whatsapp/media` is raw-binary, NOT JSON/multipart** — uses route-level `express.raw({type:()=>true, limit:"20mb"})` (the global `express.json` won't parse `video/*`), reads the Buffer body, mime from `content-type`, filename from `x-filename` header, maps mime→type, calls `uploadMedia` → `{media_id, media_type}`. Like the PDF endpoints it lives OUTSIDE Orval; the web client calls it with a direct `fetch("/api/admin/whatsapp/media", {body:file, headers:{"content-type":file.type,"x-filename":file.name}})` (cookies auto-included). 16MB cap for video.
- Secrets (all optional, graceful degrade): `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_BUSINESS_ACCOUNT_ID`, `WHATSAPP_WEBHOOK_VERIFY_TOKEN`, `WHATSAPP_APP_SECRET`. No Replit integration exists for Meta WhatsApp — creds come from the user's Meta app.

## Terms & Conditions surfaces + product-aware voucher PDF
- T&C live in `lib/voucher-content`: `VOUCHER_TERMS` (condensed, voucher PDF), `VOUCHER_TERMS_FULL` (web `/terms`, no space limit), and `DAY_PASS_TERMS` (condensed, Day Pass voucher PDF only). Keep the condensed sets in sync with the matching `VOUCHER_TERMS_FULL` section + the storefront catalog on substantive facts (prices, guest limits, validity, operating days).
- **The voucher PDF is a single A4 page with NO pagination/overflow guard** — copy growth silently clips off-page under the footer. Keep any condensed terms array roughly the size of the existing stay set.
- **PDF terms are product-aware via `ResolvedVoucher.kind` ('stay'|'day_pass').** `resolveVoucherByCode` sets it from `storeOrders.type === 'day_pass'` (storefront path); group-line and split-master paths are always `'stay'`. `buildVoucherPdf` picks `DAY_PASS_TERMS` vs `VOUCHER_TERMS`. **Why:** day passes mint store vouchers through the same pipeline, so without kind-routing a day-pass buyer's PDF would show irrelevant per-room/per-night stay terms. When `orderId` is null, kind defaults to `'stay'`.
- Day Passes are a **separate offer from the Golden Jubilee** stay voucher: no blackout dates, sold year-round, NOT operated on Tuesdays, 12-month validity (store vouchers already get `expiresAt = +365d`), Golden Fifty perk does NOT apply.

## Admin overview Day Pass stats
- `getAdminOverview()` exposes `day_passes_sold` (count of `store_order.type==='day_pass'` with `paidInstalments>=1`), `day_passes_revenue` (collected by currency), and `day_passes_by_product` breakdown. Any per-product money aggregation MUST key by product+currency (e.g. `${name}::${currency}`), never product alone. **Why:** this resort sells in SCR and EUR; keying by name alone cross-sums currencies into one row with a single mislabelled currency. Same rule applies to the matching React list key.
